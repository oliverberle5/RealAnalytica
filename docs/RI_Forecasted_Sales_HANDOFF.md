## Goal

For each real estate agent, forecast a 95%-confidence RANGE (not just a
point estimate) for their next-12-month sales, refreshed every quarter as
new data lands. Two separate targets, tracked and evaluated independently:
**dollar volume** and **unit count**. Consumers use this for revenue and
staffing/roll-up planning at the office/company level, so calibration in
aggregate matters as much as per-agent accuracy.

## Critical decisions already made (don't relitigate without reason)

1. **Two independent targets, not one.** `target_volume_next_12m` (dollars)
   and `target_units_next_12m` (count) are modeled, validated, and reported
   completely separately — different distributions (volume is far more
   skewed/outlier-prone), different business meaning. Commission/GCI was
   considered and rejected — not present in this dataset, no source for it.
2. **Target construction: self-join on t+12mo, not a new aggregation.**
   `volume_12m`/`units_12m` are already trailing-12m sums as of their own
   snapshot date, so an agent's row at time *t+12mo* directly IS the
   next-12m outcome as of time *t*. `data.py::build_targets` joins each row
   to that same agent's row exactly 12 months later. No row at t+12mo →
   dropped (see censoring decision below). This also means the two
   "source" columns (`volume_12m`, `units_12m`) stay in the feature set —
   an agent's *current* trailing pace is a legitimate, non-leaking
   predictor of their *future* pace.
3. **Forecast target = agent's total production wherever they end up**,
   not scoped to their office at forecast time. Empirically confirmed this
   requires no special handling: `volume_12m` is NOT office-scoped —
   correlation between an agent's trailing-12m volume the quarter before
   vs. the quarter of an office switch is **0.98** across 2,140 observed
   switch-quarters. The raw columns already behave as "agent-wide,"
   consistent with what we want.
4. **Censoring rule: drop any row with no resolvable t+12mo target,
   uniformly.** Mirrors the Leave model's censoring philosophy but for a
   different reason — here it's because we cannot tell, when an agent
   disappears from the RIAR panel, whether they (a) genuinely exited real
   estate (true future sales = 0, a legitimate outcome to learn from) or
   (b) moved to a brokerage/market outside what we can see (still
   producing, just invisible to us — a true zero would be wrong). **No
   field in this data distinguishes the two.** Guessing either way would
   corrupt the target for the ambiguous population, so we exclude those
   windows instead of guessing.
   **Empirically measured cost of this conservative call** (RIAR, 5,625
   agents): 770 agents (13.7%) stop appearing in the panel for good (2-
   quarter buffer applied so a temporary gap isn't miscounted as
   permanent — 725 agents/12.9% do have at least one *temporary* gap
   quarter and later reappear, confirmed NOT a fully-continuous roster).
   Of the 770 genuine dropouts, only 46 (0.8% of all agents, 2.9% of
   agents who ever switched offices) had switched offices before
   vanishing — so "switched then disappeared" is a nearly costless case to
   exclude. The other 724 (94% of dropouts) vanish with zero prior switch
   signal at all — the real ambiguous population. Net effect: 61,100
   resolved (agent, quarter) training rows survive out of a larger raw
   panel, spanning 16 usable feature-snapshot quarters (2021-10-01 through
   2025-07-01 — the last 4 quarters of the panel can't have a resolved
   target yet, by construction).
5. **Cold-start agents (<12mo history): cohort-based prior**, blended
   toward the agent's own data as it accumulates. Not yet implemented —
   flagged for the first production model, not the gut-check baseline.
6. **Range definition: empirically calibrated coverage, not a formula.**
   Goal is a backtest-verified property (~95% of actual outcomes fall
   inside the predicted range, checked quarter by quarter) — same rigor as
   the Leave model's Platt-scaling calibration work — not a distributional
   assumption like ±1.96 SE. Not yet built (see "Next up").
7. **Leave-risk score: tested as a candidate feature, not assumed useful.**
   Two-pass protocol agreed with the user: (1) build the model with NO
   leave-risk feature, measure accuracy — this is the gut-check phase,
   done below. (2) Separately, add leave-risk score as a feature, retrain,
   measure accuracy again. Only keep it, and only then decide whether it
   lives inside the point estimate/range itself or stays a side-by-side
   display figure, if it clears a real backtested improvement bar (same
   "+X, no worse than -Y on the worst fold" discipline as the Leave
   project's AutoResearch loop). **Not yet run** — this document's
   baseline results below deliberately exclude it.
8. **Forecast granularity: single next-12m total, not a quarterly path.**
   One range per agent per target, refreshed quarterly. A Q1–Q4 path was
   considered (useful for cash-flow-timed planning) but deferred — 4x the
   targets and a consistency problem (quarters need to sum sensibly to the
   annual range) not worth taking on before the core model is proven out.
9. **Retrain cadence: quarterly**, matching the Leave model's intended
   pipeline and the cadence new data actually arrives in.
10. **Same excluded/dropped columns as the Leave model, same reasons**:
    `heuristic_recruitability_score` (user: "bullshit, delete it
    entirely"), `avg_dom_12m` (confirmed broken, 59% zeros — use
    `market_avg_dom_12m` instead). Leave-model-specific label columns
    (`label_left_within_12m`, `label_days_to_move`, `label_censored`) are
    also dropped — not relevant to a sales target and would be leakage-
    adjacent if kept in some form (this is a different project's label).

## Baseline gut-check results (2026-07, round 1)

Simple-model role: Ridge regression plays the same role logistic
regression played in the Leave model — not a production candidate, just a
fast, auditable first pass to confirm the data has real signal and to give
fancier models a floor to beat. **Leave-risk score excluded**, per decision
#7. Single forward time split (train: 2021-10-01..2024-07-01, 12 quarters,
44,785 rows; test: 2024-10-01..2025-07-01, 4 quarters, 16,315 rows) —
matches how the Leave project used `split.py` for its own first gut-check
before `crossval.py` came in for real model comparison. Full forward-
chaining CV is worth building once we're comparing real candidate models,
not needed to answer "is there signal."

Three models compared: Ridge regression, naive persistence (predict
next-12m = current trailing-12m, i.e. no model at all), and naive mean
(predict the train-set average for everyone — the zero-signal floor).

|---|---|---|---|---|---|---|
| **volume** ($) | Ridge | 1,637,023 | 3,581,068 | 0.8021 | 0.6682 | 6.6830 |
| volume ($) | naive persistence | 1,738,316 | 3,577,457 | 0.8025 | 0.6383 | 7.1789 |
| volume ($) | naive mean | 3,476,903 | 8,053,469 | -0.0009 | n/a (constant) | 7.3867 |

| units (#) | naive mean | 8 | 17 | -0.0002 | n/a (constant) | 1.2316 |

**Reading these honestly:**
- Both targets clear the zero-signal floor by a wide margin (R² ~0.80–0.83
  vs. ~0.00 for predicting the average for everyone) — **the data has real,
  strong signal.** That was the actual point of this pass.
- Ridge barely beats naive persistence on RMSE/R² for either target, and
  naive persistence actually *wins* on MAE (units) and log1p-RMSE (both
  targets). Most of what a simple linear model captures is just "an
  agent's current pace predicts their future pace" — which naive
  persistence already gives you for free. **A linear model isn't adding
  much yet.**
- Ridge's edge shows up in **rank ordering** (Spearman 0.668 vs. 0.638 for
  volume) more than in point accuracy — it's better at telling top
  producers from bottom producers than at nailing the exact dollar figure,
  even though it doesn't reduce the raw error much.
- Ridge's log1p-RMSE is *worse* than naive persistence's, which is a real
  weakness, not noise: linear regression can predict negative
  dollars/units (nonsensical, clipped to 0 before scoring), and the
  clipped predictions land far from small true values in log-space. This
  is exactly the kind of failure a skewed, non-negative target causes for
  an unconstrained linear model.
- **Conclusion: proceed past the simple baseline.** The signal is there;
  the ceiling clearly isn't at R²≈0.80 with a linear model barely beating
  a persistence heuristic. See "Recommended next models" below.

## Is AUC the right metric here? No.

AUC measures a binary classifier's ability to rank positive cases above
negative cases — it has no defined meaning for a continuous target like
dollars or unit counts. It was right for the Leave model (binary: did they
leave, yes/no) and it is not applicable here. The metrics that actually
matter for this project, in order of what they're for:

- **Point-forecast accuracy**: MAE, RMSE, R² — used above. Consider also
  reporting on a log scale (log1p-RMSE) given how skewed dollar volume is
  (a few luxury-market outlier sales can dominate raw RMSE).
- **Ranking quality** (the closest analog to what AUC did for the Leave
  model — "can we tell top producers from bottom producers," which matters
  for the same kind of prioritization use case): Spearman rank correlation
  (used above), or top-decile capture (what fraction of the true top 10%
  of producers land in the model's predicted top 10%).
- **The actual deliverable — interval quality**: this is the metric that
  matters most once we build a real range-producing model, and none of the
  above measure it at all. Needs **empirical coverage** (what % of true
  outcomes fall inside the predicted 95% range — should be ~95%, checked
  per quarter like the Leave model's calibration backtest) and **pinball
  /quantile loss** (penalizes both a range that's too narrow to catch the
  truth and one that's needlessly wide) and **mean interval width**
  (sharpness — a model that's "95% right" by being absurdly wide isn't
  useful). None of this exists yet — it's the next real build target, not
  something the gut-check baseline needed.

## Range / 95% coverage analysis (2026-07, round 3)

First real look at what decision #6 (empirically calibrated 95% coverage,
not a formula) actually requires. Proper 3-way split so nothing is
measured on data it was built from: TRAIN (10 quarters, 2021-10..2024-01,
fits the XGBoost point model) → CALIBRATION (2 quarters, 2024-04..2024-07,
never trained on — residuals measured here to build candidate ranges) →
TEST (4 quarters, 2024-10..2025-07, coverage only measured here). Checking
coverage on the same data used to build the range would be circular.

Three candidate range constructions, all centered on the same XGBoost
point prediction:
1. **Naive normal**: pred ± 1.96×RMSE(calibration residuals) — the
   textbook 95% CI formula, assumes residuals are normally distributed.
2. **Empirical**: pred + [2.5th, 97.5th percentile of calibration
   residuals] — no normality assumption, same flat width for every agent.
3. **Relative**: same idea as (2) but on *relative* residuals
   (residual/prediction), so the band's width scales with the size of the
   prediction instead of being flat.

| target | range type | overall coverage | avg width | vs. naive |
|---|---|---|---|---|
| volume | naive normal | 94.9% | $7,459,352 | — |
| volume | empirical (flat) | 93.7% | $8,061,523 | +8.1% |
| volume | relative (scaled) | 97.5% | $11,458,613 | +53.6% |
| units | naive normal | 96.7% | 18.2 | — |
| units | empirical (flat) | 95.0% | 16.5 | -9.0% |
| units | relative (scaled) | 98.7% | 28.4 | +56.4% |

**The overall-coverage numbers are misleading on their own — this is the
actual finding.** Both flat bands (naive and empirical) look fine at
~94-97% *on average*, but breaking coverage down by predicted-size tercile
exposes that the flat band is only "right" in aggregate by averaging two
opposite failures:

| target | tercile | naive coverage | naive width | relative coverage | relative width |
|---|---|---|---|---|---|
| volume | smallest-predicted 1/3 | **99.7%** (way over) | $5,982,703 | 95.7% | **$2,223,664** |
| volume | middle 1/3 | 99.0% (over) | $6,803,989 | 97.8% | $5,268,181 |
| volume | largest-predicted 1/3 | **86.1%** (under target) | $9,590,971 | 99.2% | **$26,881,156** |
| units | smallest-predicted 1/3 | **99.7%** (way over) | 14.5 | 97.1% | **6.2** |
| units | middle 1/3 | 99.5% (over) | 16.7 | 99.0% | 14.7 |
| units | largest-predicted 1/3 | **90.8%** (under target) | 23.3 | 99.8% | **64.5** |

A flat band gives the bottom two-thirds of agents (typical/small
producers) a needlessly wide, unconvincing range (99%+ actual coverage —
way more margin than 95% requires) while simultaneously **undercovering
the top third of producers** (86.1%/90.8% actual, below the 95% target) —
exactly the highest-revenue-impact agents for the stated staffing/revenue-
planning use case. Confirmed by the heteroscedasticity check: correlation
between predicted size and absolute miss is 0.594 (volume) / 0.665
(units) — big producers really do have bigger absolute swings, so a
single global width is structurally the wrong shape of range, independent
of whether its *average* coverage happens to land near 95%.

**The size-scaled ("relative") band fixes the shape, not just the
average**: coverage becomes much more even across terciles (95.7% /
97.8% / 99.2% for volume) instead of swinging from 99.7% to 86.1%. The
practical consequence directly answers "how much do ranges widen": **not
uniformly.** The bottom two-thirds of agents — most of the roster — would
actually get a *narrower*, more precise-feeling range than a flat band
gives them today ($2.2M–$5.3M vs. a flat $6.0M–$6.8M for volume; 6.2–14.7
units vs. a flat 14.5–16.7 units). The widening is concentrated on the
top third of producers, whose absolute range genuinely needs to be much
bigger ($26.9M vs. $9.6M for volume) to honestly reflect how much more
their production swings year to year — and even then, the flat band was
still undercovering them at that width, so this isn't overcaution, it's
correcting a real gap.

**Caveats, not yet resolved:**
- Single train/calibration/test split (2 calibration quarters). Same
  gap as the point-estimate round-1/2 results — worth re-checking with
  multiple forward-chaining calibration windows before treating any of
  these exact numbers as final, same rigor the Leave model applied via
  `crossval.py`.
- The "relative" band is a cheap proxy for the real fix, not the final
  answer — it only scales width by *predicted size*, when a proper
  quantile regression model (see "Recommended next models," item 2) could
  let the band's shape depend on other volatility signals too (e.g.
  tenure, career stage, price-mix concentration) instead of size alone.
- All bands here clip the lower bound at 0 (sales can't be negative) —
  noted since it mechanically helps small-agent coverage look better than
  an unclipped band would.

## Real quantile regression + conformal calibration (2026-07, round 4)

Round 3's "relative" band was an explicitly-flagged proxy (scale a flat
band by predicted size only). This round builds the real thing: three
separate XGBoost models trained directly on the 2.5th/50th/97.5th
percentiles (`objective="reg:quantileerror"`), so the band's shape can
depend on any feature the model finds predictive of volatility — tenure,
office/company size, price mix, etc. — not just predicted size. Then
**conformalized quantile regression (CQR)**: measure, on the calibration
set the quantile models never trained on, how far outside the raw band
the truth actually fell, and shift both edges by that amount. Same
train/calib/test split as round 3, same reasoning for why (coverage is
only trustworthy measured on data the band-building process never
touched).

| target | band | overall coverage | avg width | coverage range across size terciles |
|---|---|---|---|---|
| volume | raw quantile model | 89.4% | $6,674,700 | 88.5%–90.8% (tight spread) |
| volume | + CQR | 92.4% | $6,753,453 | 89.7%–95.1% (tight spread) |
| units | raw quantile model | 92.2% | 14.0 | 91.1%–93.5% (tight spread) |
| units | + CQR | 97.1% | 16.5 | 94.4%–98.9% (tight spread) |

**Compare to round 3's flat naive band**: 94.9% overall but swinging from
99.7% (smallest agents, way over-covered) to 86.1% (largest agents,
under-covered) — a huge spread. The real quantile model's coverage spread
across terciles is far tighter (88.5–90.8% raw, before any calibration
correction at all) — **this is the actual fix round 3 was gesturing at**:
letting the model learn per-agent volatility directly beats scaling a
single band by size alone. And it does this at roughly the SAME width as
the flat band ($6.67M vs. $7.46M) — not the +53.6% blowup the crude
"relative" proxy required to get similar evenness. Properly-shaped ranges
turned out to be cheaper, not more expensive, than the proxy suggested.

**CQR did not land exactly on 95% overall** (92.4% volume, 97.1% units —
undershoots one, overshoots the other) despite being a method that
carries a theoretical coverage guarantee. Most likely explanation, not
yet confirmed with more folds: the guarantee assumes the calibration and
test data are "exchangeable" (similarly distributed) — here they are
time-separated by design (calibration: 2024-04..2024-07; test:
2024-10..2025-07, i.e. up to a year later), so genuine market
drift between those windows can violate that assumption. **This is the
same phenomenon already root-caused in the Leave model's calibration
work** (`../Likelihood_to_Leave_Algorithm/modeling/HANDOFF.md`, calibration
section) — lagging calibration under real-world drift, not a bug in the
method. It argues for the same fix already agreed for this project
(decision #9, quarterly retrain): refresh the conformal adjustment every
quarter using the most recently completed quarter's actual outcomes,
rather than freezing one calibration measurement. Not yet built as a
pipeline.

**Bonus finding**: the median-quantile model's point accuracy (MAE
$1,577,705 volume / 3.3 units) is essentially on par with round 2's
dedicated squared-error XGBoost model (MAE $1,608,699 volume / 3 units) —
suggesting we could unify to one model family (three quantile models)
instead of maintaining a separate point-estimate model plus a bolted-on
band. Not yet decided — worth confirming across more folds first.

**Not yet done**: multi-fold validation of all of the above (single
split only, same caveat as every round so far); deciding whether to unify
point-estimate and range into one quantile-model family; the actual
quarterly-refresh conformal recalibration pipeline.

## AutoResearch: model/hyperparameter search (2026-07, round 6)

Ran a full autonomous search — `AutoResearch/program.md` (rules) +
`AutoResearch/autoloop.py` (driver), same operating pattern as the Leave
project's own autoresearch loop, retargeted from an AUC objective to a
quantile-regression one. 16 candidates queued (model families:
XGBoost/CatBoost quantile regression; hyperparameter sweeps; bottom-N
feature pruning; log1p-target transform; a monotonic-constraint variant;
two blends), evaluated on the identical round-4/5 train/calib/test split
and CQR procedure. Objective: **composite score** = average of 6
pinball-loss ratios (3 quantiles × 2 targets) vs. the round-4/5 baseline,
kept only if composite improves >0.5% AND coverage stays ≥85% for both
targets AND tercile-coverage spread stays ≤15pts for both (guards against
"better on average, worse-shaped" — the exact failure mode diagnosed in
round 3). Full log: `AutoResearch/results.tsv`.

**Result: 3 kept, 12 discarded, 1 crash.** Winner by composite:
**CatBoost quantile regression, depth=4** (`catboost_d4`, composite
0.9532 — a ~4.7% average pinball-loss improvement).

| config | vol. coverage | vol. pinball (lo/med/hi) | vol. tercile spread | units coverage | units pinball (lo/med/hi) | units tercile spread |
|---|---|---|---|---|---|---|
| baseline (XGBoost d5, round 4/5) | 92.4% | $83,792 / $788,853 / $265,945 | 5.4pts | 97.1% | 0.18 / 1.63 / 0.45 | 4.4pts |
| xgb_depth4 | 92.4% | $82,856 / $797,707 / $246,513 | 5.3pts | 97.1% | 0.18 / 1.65 / 0.43 | 4.4pts |
| **catboost_d6** | 92.4% | $87,250 / $795,358 / $244,912 | **4.9pts (better)** | **97.9%** | 0.18 / 1.61 / **0.39 (best)** | **3.5pts (better)** |
| **catboost_d4 (composite winner)** | **92.6%** | **$80,736** / $801,709 / **$237,192 (best)** | 6.8pts (worse) | **97.9%** | 0.18 / 1.62 / 0.40 | 3.1pts (better) |

**Reading this honestly — the composite winner isn't a clean win on
every axis.** `catboost_d4` posts the best tail-quantile accuracy (lo/hi
pinball loss — the numbers that most directly describe range-edge
quality) but its volume tercile-coverage spread gets *worse* than the
baseline (6.8pts vs. 5.4pts), meaning it's slightly less evenly
calibrated across small vs. large producers than what round 4 already
had — the composite metric doesn't directly reward evenness, only
guards against it blowing past 15pts, so a config can "win" while quietly
giving some of that back. **`catboost_d6` is the more balanced pick**:
smaller composite gain, but it improves tercile spread on BOTH targets
(4.9pts/3.5pts, both better than baseline) while still beating baseline
on 4 of 6 pinball numbers. **Recommendation: adopt `catboost_d6` as the
new production model family** (real, broad-based improvement, no
give-back) rather than chasing `catboost_d4`'s marginally better
composite at the cost of the evenness property round 3/4 specifically
fixed. Either way, **CatBoost, not XGBoost, is now the better quantile-
regression family for this target** — a genuinely new finding, not
something the earlier rounds had reason to suspect (round 2's model
comparison only used CatBoost for the squared-error point model, never
for quantile regression specifically).

**Everything else discarded, and why (see `results.tsv` for full
numbers)**: deeper trees (depth 6) and heavier L2 regularization on
XGBoost both landed worse than baseline; slower/faster learning-rate
variants were all within noise of baseline; feature pruning (dropping
the bottom 20 or 40 features) didn't help — consistent with round 2's
finding that a handful of features (own trailing volume/units) already
dominate, so trimming the long tail of minor features doesn't move the
needle; the log1p-target transform (mathematically valid for quantiles —
they commute with monotonic transforms) didn't help either, suggesting
the tree models were already handling the skew reasonably via their
native split structure rather than needing a scale change; both blends
(XGBoost+CatBoost, XGBoost+log1p-XGBoost) landed between their parents,
as expected, not better than the better parent alone.

**One real crash, worth keeping as a documented finding**: XGBoost
quantile regression (`reg:quantileerror`) combined with a monotonic
constraint (forcing the predicted quantile non-decreasing in the agent's
own current trailing volume/units) took **over 36 minutes** and was
killed at the 5-minute cap — versus ~1-2 minutes for every other XGBoost
candidate in the queue. Not investigated further (out of scope for this
run), but worth flagging for anyone tempted to add monotonic constraints
to a quantile objective in XGBoost specifically: the pinball loss's
non-smooth gradient likely interacts badly with XGBoost's exact
monotonic split-finding, unlike the smooth squared-error case where
monotonic constraints are cheap (this is exactly the setup the Leave
model uses successfully for its classifier, which uses Logloss, not a
quantile objective).

**Not yet done**: this used the same single train/calib/test split as
every round so far, still the biggest open caveat across this whole
document — a real production decision should re-run at least the top 2-3
configs (`catboost_d6`, `catboost_d4`, baseline) across multiple
forward-chaining calibration windows before finalizing. The composite
objective also currently weights all 6 pinball numbers equally; worth
revisiting whether the business cares more about tail accuracy (range
edges) or median accuracy before treating that weighting as final.

## Multi-fold validation (2026-07, round 7) — REVISES round 6's recommendation

Round 6 flagged its single split as the biggest open caveat. This round
closes that gap: `AutoResearch/multifold_validation.py` builds 4
expanding-window folds (train 6/8/10/12 quarters, calib 2 quarters, test
2 quarters each, non-overlapping test windows spanning
2023-10-01..2025-07-01) and re-runs the baseline (XGBoost d5), and both
round-6 keepers (CatBoost d6, CatBoost d4) on every fold, using the
identical quantile+CQR procedure as every prior round.

| candidate | mean composite | worst-fold composite | folds beating baseline |
|---|---|---|---|
| baseline (XGBoost d5) | 1.0305 | 1.1184 | — |
| catboost_d6 | 1.0171 | 1.0869 | **3 of 4** (loses in fold 1: 1.0712 vs. baseline's 1.0524) |
| **catboost_d4** | **0.9864** | **1.0602** | **4 of 4 — clean sweep** |

**This reverses round 6's recommendation.** On the single split, `catboost_d4`
had the best raw accuracy but a worse volume tercile-coverage spread than
baseline (6.8pts vs. 5.4pts), which read as a real trade-off, so
`catboost_d6` — which improved evenness too on that one split — was
recommended as the "safer" choice. Across 4 independent folds, that
doesn't hold up:

- **`catboost_d4` beats the baseline in every single fold** on the
  composite metric (0.9947/1.0602/0.9579/0.9326 vs. baseline's
  1.0524/1.1184/0.9975/0.9536) — the strongest possible evidence short of
  a full production backtest: not just a better average, a fold-by-fold
  sweep.
- **`catboost_d6` is a mixed bag** — it beats baseline in 3 of 4 folds but
  is actually *worse* than baseline in fold 1 (1.0712 vs. 1.0524).
- **The volume tercile-coverage spread that drove round 6's "d6 is safer"
  call turns out to be noisy for EVERY model, not specifically worse for
  d4**: baseline's own spread swings from 2.1% (fold 4) to 8.9% (fold 1)
  across folds — a wider range than the gap between d4 and d6 on any
  single fold. Round 6's read of that one split's spread difference as a
  meaningful evenness trade-off doesn't survive contact with more data —
  it was mostly which-fold-you-happened-to-land-on noise, not a real
  property of `catboost_d4` specifically. (Units tercile spread, by
  contrast, is consistently a little better for both CatBoost variants
  across all 4 folds — that part of round 6's finding does hold up.)

**Revised recommendation: `catboost_d4` is the production choice**,
correcting round 6's `catboost_d6` call now that real multi-fold evidence
is in. Documenting the correction rather than quietly overwriting it —
round 6's reasoning was sound given what it had (one split), it just
turned out to be measuring fold-specific noise it had no way to detect
with only one data point. This is exactly why the caveat was flagged at
the end of every round so far; it was a real gap, not boilerplate.

**Not yet done**: still only 4 folds (limited by only 16 usable quarters
total split three ways per fold) — a genuine production commitment
should keep monitoring per-quarter coverage going forward (ties into the
still-unbuilt quarterly-refresh pipeline, decision #9) rather than
treating even this multi-fold result as the final word. Hyperparameters
were not re-tuned per fold (same depth=4 CatBoost config used everywhere)
— an even more thorough pass would re-run round 6's full autoresearch
queue per fold, not just the two winners; not done here given the time
cost (4 folds x 16 candidates was judged not worth it when the 2-model
check already gives a clear, actionable answer).

## Quarterly refresh pipeline (2026-07, round 8) — decision #9 resolved

`modeling/score_agents.py` is the first runnable end-to-end production
script (everything before this was research/comparison scripts, same gap
the Leave model itself still has per its own HANDOFF.md). Uses

| d3, 3-seed ensemble average | 0.978 (confirmed via standalone retry) | 1.045 | same near-miss pattern |

## AutoResearch round 3 follow-up (2026-07-18, round 11) — new production winner: log1p-target CatBoost d3

Round 10 flagged the log1p-target transform (round 6 only ever tested it
on XGBoost, where it didn't help) as an untested angle specifically on
CatBoost, the model family that's actually been production since round

across model families without re-checking — the two GBM implementations

guaranteed to transfer.

## Cold-start cohort-prior blend (2026-07-21, round 12) — RESOLVED: tested, discarded

Decision #5 (cohort-based prior for agents with <12mo career, blended
toward the agent's own model prediction as real data accumulates) had
been flagged as "not yet implemented" since the project's early
assumption-gathering. Built it (`modeling/cohort_prior.py`) and tested it
properly before trusting it, same "test it, don't assume it helps"
discipline as round 5's leave-risk-score experiment and round 9's
volatility-feature experiment.

**Design**: for agents with `career_months < 12`, blend the raw log1p
CatBoost d3 quantile prediction with a cohort prior — the empirical
(2.5th/50th/97.5th percentile) outcome among historically-new agents
(also `career_months < 12` at the time) at the same `office_brand`, or a
pooled all-brands fallback when a brand has fewer than 30 historical
cold-start comps. Blend weight = `career_months / 12`, so a brand-new
agent (0 months) leans almost entirely on the cohort prior and an
11-month agent leans almost entirely on their own model prediction — the
blend fades out smoothly, not a hard cutoff.

**Evaluated on the cold-start SUBSET specifically** (not overall
composite, which barely moves either way by construction since
cold-start agents are only ~9% of any fold's test set) —
`AutoResearch/evaluate_cohort_prior.py`, same 4 folds as every round
since 9.

| target | fold | cold-start rows | raw model pinball total | blended pinball total | change |
|---|---|---|---|---|---|
| volume | 1 | 701 | $748,629 | $831,207 | **+11.0% (worse)** |
| volume | 2 | 653 | $641,229 | $704,156 | **+9.8% (worse)** |
| volume | 3 | 691 | $853,379 | $888,395 | **+4.1% (worse)** |
| volume | 4 | 733 | $676,866 | $804,635 | **+18.9% (worse)** |
| units | 1 | 701 | 1.92 | 2.05 | **+6.9% (worse)** |
| units | 2 | 653 | 1.74 | 1.90 | **+9.1% (worse)** |
| units | 3 | 691 | 1.83 | 2.17 | **+19.0% (worse)** |
| units | 4 | 733 | 1.83 | 2.22 | **+22.0% (worse)** |

**Worse in all 8 fold/target combinations, no exceptions.** Coverage
ticked up slightly in most folds with blending (e.g. units fold 1: 92.2%
→ 96.1%), but the raw model's coverage was already reasonably close to
95% on its own in most folds — the blend "fixes" a coverage gap that
mostly wasn't large to begin with, at the cost of substantially wider,
less precise ranges (pinball loss up 4-22%).

**Why this makes sense in hindsight**: the model already has
`career_months` itself as a raw feature, plus `cohort_volume_quartile`,
office/company context, and everything else — a tree model is free to
learn "agents like this, this early in their career, tend to look like
X" directly from the full feature set, agent by agent. Replacing that
individualized read with a coarser brand-level averaged prior throws away
exactly the information the tree model was already using well.
**Consistent with round 9's finding on the volatility feature**: a
plausible, carefully-built, leak-safe intervention that assumes the
model needs help it turns out it already doesn't need. Two rounds in a
row now where "let's hand-hold the model with domain-motivated
post-processing" has lost cleanly to "trust what the tree model already
learned from the raw features."

**Resolution**: decision #5 is now "tested, discarded" — no cohort-prior
blending in production. `modeling/cohort_prior.py` and
`AutoResearch/evaluate_cohort_prior.py` are kept on disk as documented,
working, honest-negative-result code (same convention as
`rebrand_classifications.py`'s audit trail in the Leave project) — not
wired into `score_agents.py`, no production changes this round.

## Multi-level production output (2026-07-21, round 13)

Decision: offer a fixed menu of confidence levels rather than a single
95% output or a fully continuous slider — **50/65/70/75/80/95%**, chosen
deliberately (not evenly spaced): denser in the 50-80% "cheap zone" the
confidence-level sweep (round from `confidence_level_analysis.html`)
identified, capped at 95% rather than extending to 96-99%, which that
same analysis showed is a poor trade (cost per point of confidence
roughly 10-20x higher up there than in the 50-80% band).

**Efficient by construction, not just by picking few levels**: the point
estimate (median) doesn't depend on confidence level at all, so
`forecast_target_multi()` fits it ONCE per target and reuses it across
every bucket. Only the lo/hi quantile pair is refit per level (CatBoost's
quantile loss is fit per-alpha; there's no way to derive one alpha's
model from another's). Total cost: `1 + 6*2 = 13` fits per target (26
total for both targets) — versus a naive "all 49 whole percents" design,
which would need `1 + 49*2 = 99` fits per target and still only cover
integer percentages.

**Output is one wide spreadsheet, not 6 files**: `current_agent_sales_forecast.csv`,
one row per agent, 31 columns — id columns, one shared point estimate
per target, and a `{target}_min_{level}`/`{target}_max_{level}` column
pair per bucket (e.g. `volume_min_65`, `volume_max_65`). Verified the
bounds shrink monotonically toward the point estimate as the level drops
from 95% to 50%, for a representative (median) agent:

| level | volume range | units range |
|---|---|---|
| 95% | $0 &ndash; $3,860,419 | 0.0 &ndash; 10.9 |
| 80% | $0 &ndash; $2,476,911 | 0.0 &ndash; 8.1 |
| 75% | $0 &ndash; $2,200,387 | 0.2 &ndash; 7.1 |
| 70% | $2 &ndash; $1,976,030 | 0.4 &ndash; 6.3 |
| 65% | $1 &ndash; $1,819,160 | 0.5 &ndash; 5.9 |
| 50% | $131 &ndash; $1,439,736 | 0.9 &ndash; 5.2 |

**Not yet done**: a real front-end dropdown reading this CSV (the
interactive artifacts so far are demonstrations, not wired to live
production output); a formal decision on whether the eventual UI offers
exactly these 6 levels or lets users interpolate between them
client-side (discussed, not built).

## Realistic-floor snap + corrected $0-floor rates (2026-07-21, round 14)

User feedback on the production CSV: some agents' `volume_min_*` columns
showed values like $131, $2, $1 — technically "not exactly $0" but
nonsensical as real outcomes (no home sells for $131). This is not a
clipping bug (clipping at 0 was already correct) — it's the raw quantile
model outputting a small positive number that happens to fall between
$0 and the smallest realistic transaction size, which is meaningless
precision for a continuous regression applied to a target that's
actually "either $0 or at least the price of one home."

**Fix, grounded in real data, not an arbitrary round number**:
`score_agents.py::compute_realistic_floor()` computes the 1st percentile
of historically observed NON-ZERO `target_volume_next_12m` values, fresh
from the current resolved training data every run (self-updating, same
spirit as the rest of this pipeline) — **$190,000** this run. Any
predicted `min` strictly between $0 and that floor is snapped DOWN to
exactly $0 (`snap_unrealistic_floor()`) — down, not up to the floor
itself, since the honest reading of a tiny-but-nonzero prediction is
"most likely no sales at all," not "guaranteed at least $190K." Applied
to volume only, not units — a 0.2-unit lower bound is already a normal,
accepted way to express "usually zero, occasionally one," not a broken-
looking number the way a fractional dollar figure is. Wired into both
`score_agents.py` (production CSV) and `sweep_confidence_levels.py` (the
confidence-level analysis), reusing the same two functions in both so
the fix can't drift out of sync between them.

**This surfaced a real correction to every $0-floor-rate figure reported
earlier in this document and in `confidence_level_analysis.html`** — those
numbers only counted LITERAL zero, silently undercounting because values
like $131 didn't register as "zero" even though they were functionally
meaningless as anything else:

| level | old (literal-$0-only) volume $0-floor rate | corrected rate |
|---|---|---|
| 50% | 9.7% | 57.7% |
| 65% | 16.5% | **73.9%** |
| 75% | 26.7% | 77.7% |
| 95% | 67.2% | 91.1% |

**Root-caused, not just patched**: checked directly against history
whether these high rates reflect something real. **About 22% of all
61,100 historical agent-years in this dataset have genuinely $0 sales
volume** (13,358 rows) — and this is not a stable base rate, it has
climbed steadily from **16.4%** (2021-10 quarter) to **24.7%** (2025-07
quarter) across all 16 quarters, a real trend, not noise. The corrected
$0-floor rates at lower confidence levels are large because a large and
growing share of the actual roster genuinely produces nothing in a given
year — the fix didn't invent this, it stopped hiding it behind
nonsense-precision dollar figures. Worth flagging to whoever owns
roster/recruiting decisions as a separate, real finding: a rising
zero-production rate is a business signal in its own right, independent
of anything this forecasting project set out to measure.

**Not yet done**: `compare_precision_levels.py` (the standalone 50/75/60
script from earlier rounds) was NOT updated with this fix — it's
superseded by `sweep_confidence_levels.py`'s finer sweep for all
practical purposes now, so re-patching it wasn't judged worth the time;
flagged here so nobody trusts its output as floor-corrected without
checking first.

## Why $0 floors are so common, and the planned fix (2026-07-21, round 15) — NOT YET BUILT

User pushback after round 14's correction: nearly 3/4 of agents showing a
$0 floor at 65% confidence feels regrettable, given the roster-wide
historical base rate of genuinely-$0 outcomes is only ~22% (round 14).
Investigated whether this is a defect before proposing a fix.

**Root cause, confirmed empirically, not a bug**: the 22% figure is a
*population average* — pulled down by established producers who almost
never hit $0. It is fully consistent with that average for a *majority*
of individual agents to carry a meaningfully higher personal zero-sales
risk. Tested directly by fitting the lower bound at a range of fixed
percentiles (log1p CatBoost d3, current roster, floor-snap from round 14
applied throughout):

| lower bound percentile | % of agents floored at $0 |
|---|---|
| 20th | 70.1% |
| 25th (~today's 50% bucket) | 57.7% |
| 30th | 57.0% |
| 35th | 42.0% |
| 40th | 37.9% |
| 45th | 28.0% |
| 50th (median) | 21.4% |

**Even at the 25th percentile, a majority of the roster is still at
$0** — meaning most agents individually carry >25% zero-sales risk, well
above the 22% roster average. Not a modeling artifact; the model is
accurately reporting a real, skewed distribution of individual risk.

**Why simply moving the lower bound isn't a clean fix**: coverage =
(upper percentile) − (lower percentile). Pushing the lower bound up to
the 35th percentile while keeping a stated "65%" label would require the
upper bound to stretch to roughly the 100th percentile to compensate —
not practically usable. The only honest paths are (a) quietly relabeling
the confidence level down to whatever it actually is once the lower
bound moves (rejected — papers over the issue rather than fixing it), or
(b) presenting an explicitly asymmetric range ("70% chance above this
floor, 95% chance below this ceiling") instead of one clean percentage
(statistically fine, just a less tidy UI).

**Decision: build a two-part ("hurdle") presentation instead, later —
not an asymmetric-quantile relabeling.** Split the forecast into two
honest, separate numbers rather than making one range do both jobs:

1. **P(zero sales this year)** — reported directly and explicitly as its
   own percentage, not buried inside a range. This is the standard
   approach for "mostly continuous, sometimes exactly zero" targets (a
   hurdle/zero-inflated model structure) — real estate sales are exactly
   this shape.
2. **A conditional nonzero range** — "if they sell anything, expect
   $X&ndash;$Y" — computed on the subset of historical outcomes that
   weren't $0, so it's NEVER $0 itself and always carries real
   information, rather than being swamped by the population's zero mass.

This doesn't hide the zero-sales risk (it's arguably more visible than
before, as its own explicit number) — it stops that risk from making the
rest of the range look uninformative. User's read: "tremendous... we
will build it later." **Not yet implemented** — no code changes this
round. When picked up, needs: (a) a P(zero) estimator (likely a simple
classifier on the resolved training data, `target_volume_next_12m == 0`
as the label — conceptually adjacent to, but a new model from, the Leave
model's classifier), and (b) refitting the existing quantile machinery
on the nonzero-only subset of `target_volume_next_12m` for the
conditional range.

## Hurdle split implemented (2026-07-21, round 16) — decision from round 15 built

Round 15 proposed, but didn't build, splitting each target's forecast into
two honest numbers instead of one range doing both jobs. Built this round:
`modeling/hurdle_model.py`, wired into `modeling/score_agents.py`.

**Two separate hurdles, not one shared "inactive" flag.** Checked first
whether volume==0 and units==0 are the same event before assuming one
classifier could serve both: they're correlated but not identical — every
row with `units_next_12m==0` also has `volume_next_12m==0` (0 counter-
examples), but 3,579 of 61,100 resolved rows (5.9%) have `volume==0` with
`units>0` (plausible: $0-recorded transactions like rentals/assignments
that still count as a unit). Same "two independent targets" discipline as
decision #1, so volume and units each get their own P(zero) classifier and
own conditional-nonzero range, not one combined flag.

**P(zero)**: CatBoost classifier (`auto_class_weights="Balanced"`, since
base rates are 24.3% volume / 16.5% units — moderate but real imbalance),
trained on the same train-quarters window as the quantile models, then
**isotonic-calibrated** on the held-out most-recently-completed calibration
quarters — same train-on-early/correct-on-recent pattern the CQR conformal
adjustment already uses for the quantile bounds, applied here because
`Balanced` class weights deliberately distort raw predicted probabilities
during training to fight imbalance, so the raw output isn't trustworthy as
a probability on its own until corrected against held-out ground truth.

**Conditional-nonzero range**: `forecast_conditional_nonzero()` reuses
`score_agents.py::forecast_target_multi()` completely unmodified, just
called with `resolved` pre-filtered to rows where that target was actually
nonzero — every quantile fit and every conformal-calibration measurement
is then implicitly conditioned on "given they sold something." The
existing realistic-floor snap (round 14) needed one behavior change for
this path: `snap_unrealistic_floor()` gained a `direction` parameter —
`"down"` (unchanged default, used by nothing anymore in production but
kept for any future unconditional caller) snaps a too-small prediction to
exactly 0, `"up"` (used here) snaps it UP to the floor instead, since 0 is
not a valid answer in a conditional-on-nonzero range by construction.

**Production output changed**: `current_agent_sales_forecast.csv`'s
`{label}_point_estimate` and `{label}_min_{level}`/`{label}_max_{level}`
columns are now the CONDITIONAL-on-nonzero numbers (never $0), with a new
`{label}_pct_zero` column carrying the calibrated zero-probability
separately — replacing, not adding to, the old unconditional columns
(same compute cost, ~13 fits + 1 classifier per target, since the
unconditional pass round 15 wanted to retire is simply not run anymore).
Verified end-to-end on the current snapshot: e.g. a representative
(median-by-volume) agent now reads "28.0% chance of $0 volume this year;
if they sell anything, expect $661,996–$2,024,384 at 50% confidence"
instead of a single range whose low end was $0 or a snapped-to-$0 value
that obscured how much real signal was underneath it.

**Not yet done**: multi-fold validation of the P(zero) classifier's
calibration quality specifically (empirical coverage checked for the
quantile bounds across 4 folds as of round 7, but the isotonic-calibrated
zero-probability itself hasn't had its own backtested Brier-score/
calibration-curve check yet); no UI wired to present the two-number
hurdle format to end users (still a CSV).

## P(zero) autoresearch + production rewire (2026-07-21, round 17)

Round 16 shipped the hurdle split with a single reasonable-but-untuned
classifier config (CatBoost depth=4) — the P(zero) side never got the
search-plus-multi-fold-validation treatment the quantile range went
through across rounds 6/9/10/7. Closed that gap: `AutoResearch/autoloop_pzero.py`,
same 4-fold forward-chaining structure as every quantile search since
round 9. Full log: `AutoResearch/results_pzero.tsv`.

**Concrete measurable: Brier score** (mean squared error between the
calibrated P(zero) probability and the actual 0/1 outcome, on held-out
test quarters) — a strictly proper scoring rule, so a config can only
improve it by being genuinely better-calibrated AND better-discriminating
at once, not by gaming one at the other's expense. Composite = mean of
the volume/units Brier-ratio-vs-baseline (same construction as the
quantile search's pinball-ratio composite). AUC tracked as a
non-regression guard against a config that shrinks Brier by collapsing
toward the base rate for everyone (a calibration illusion, not a real
improvement) — same role the tercile-spread guard plays for the
quantile range.

14 candidates queued around the round-16 CatBoost-d4 baseline: depth
2-4-5-6, learning-rate/L2 sweeps, `auto_class_weights` variants (None,
SqrtBalanced), Bernoulli subsampling, bottom-30 feature pruning, a
monotonic constraint (P(zero) non-increasing in the agent's own current
trailing volume/units), an XGBoost cross-family check, and a
CatBoost+XGBoost blend.

**Result: 1 kept, 13 discarded.** Winner: **XGBoost depth=4**
(`scale_pos_weight`-balanced), composite 0.9940 (mean Brier ratio) /
1.0071 (worst-fold) — clears the 0.5%-improvement-vs-1%-worst-fold-
regression bar.

| | volume P(zero) Brier | units P(zero) Brier | volume AUC | units AUC |
|---|---|---|---|---|
| baseline (CatBoost d4) | 0.13476 | 0.10152 | 0.8256 | 0.8597 |
| **XGBoost d4 (winner)** | **0.13333 (−1.06%)** | 0.10138 (−0.14%) | **0.8289** | 0.8599 |

Not a calibration trick: AUC held flat-to-better on both targets (the
guard several near-miss candidates failed on worst-fold, not AUC — e.g.
`catboost_noweight` posted an even better mean composite (0.9926) but
its worst fold regressed to 1.0120, past the 1.01 tolerance). Same
"CatBoost wins the quantile range (round 11), XGBoost wins the
classifier" split the Leave-model-adjacent literature would predict —
the two hurdle halves were tuned, and won, completely independently;
nothing requires them to land in the same model family.

**Production rewired**: `modeling/hurdle_model.py::fit_zero_classifier`
now fits `XGBClassifier` (depth=4, `scale_pos_weight` computed fresh per
fit from the fold's own class balance — not a hardcoded ratio, since
round 14 already established the zero-rate isn't fixed over time)
instead of CatBoost. The isotonic-calibration step downstream is
completely unchanged (it was already model-agnostic). Re-ran
`score_agents.py` end-to-end: pipeline mechanics unaffected, only the
classifier changed — e.g. the representative (median-by-volume) agent's
units P(zero) moved from 35.7% (CatBoost) to 19.5% (XGBoost) for that
specific agent, consistent with a real accuracy change, not noise (a
purely cosmetic swap wouldn't move an individual prediction that much).

**Output format unchanged, confirmed still simple-by-design**: one row
per agent, `current_agent_sales_forecast.csv`, 33 columns —
`{volume,units}_pct_zero` plus a point estimate and min/max pair per
confidence level, all conditional-on-nonzero (round 16) so the range
columns can never show $0 themselves; `volume_min_*` still uses the
raise-to-floor snap (never down to 0) confirmed intact this round, not
something that needed re-doing.

**Not yet done**: the P(zero) classifier's own calibration curve/ECE
has not had a dedicated backtested check (Brier score bundles
calibration and discrimination together but doesn't diagnose which one
would explain a regression); no re-tuning of `catboost_d3`'s quantile-
range hyperparameters was attempted here (correctly judged out of scope
per this round's own reasoning in the prior turn — the nonzero-only
subset isn't structurally different enough to expect a different
winner).

## Recommended next models

Reasoning tied directly to what the baseline exposed, not a generic list:

1. **Gradient-boosted trees (XGBoost/CatBoost) as the point-estimate
   upgrade.** Same infra/experience as the Leave model. Should capture the
   nonlinear effects a linear model can't (e.g. mean-reversion for agents
   coming off an unusually big or small year, ramp-up/down curves around
   tenure, office-switch effects) — exactly the gap between Ridge's R²
   ceiling and where a tree model likely lands.
2. **Quantile regression objective (not just point prediction) to build
   the actual range.** Train at the 2.5th/50th/97.5th percentiles directly
   (pinball loss) using XGBoost/CatBoost/LightGBM's native quantile
   objectives, or **CatBoost's native uncertainty mode**
   (`RMSEWithUncertainty`/virtual ensembles) which was already validated as
   working well with this exact data family in the Leave project. This is
   the more direct path to a calibrated range than a formula-based
   interval around a point estimate.
3. **Conformalized quantile regression (CQR)** as a wrapper on top of (2)
   if the raw quantile model's backtested coverage isn't close enough to
   95% — CQR adjusts quantile predictions post-hoc using a held-out
   calibration set to guarantee coverage empirically, which maps directly
   onto decision #6 (calibrated coverage, not a formula) without having to
   get the underlying quantile model perfectly calibrated on its own.
4. **Handle the skew/non-negativity explicitly, not just by clipping.**
   Ridge's worst failure mode (log1p-RMSE, negative predictions) comes
   from using an unconstrained linear model on a non-negative, heavy-
   tailed target. Worth testing: training the point-estimate model on
   `log1p(volume)`/`log1p(units)` and back-transforming, or a **Tweedie
   regression objective** (built for exactly this shape of target —
   semi-continuous, zero-inflated-ish, right-skewed dollar amounts; this
   is the standard tool for insurance-claim-style targets and volume looks
   structurally similar). XGBoost/LightGBM both support a Tweedie
   objective natively.
5. **For units specifically (count data): consider a Poisson or Negative
   Binomial objective** as an alternative/complement to Tweedie — units is
   a small non-negative integer count, closer to classic count-regression
   territory than volume is.

## Team-account contamination (2026-07-24 diagnosed, 2026-07-28 FIXED)

**Cross-project finding, currently fully live and unaddressed in this
project's production output. Do not lose track of it.** This project's
own round-8 HANDOFF entry already noticed a symptom of this ($115.7M
point estimate traced to a "$162M-trailing-12m/310-unit... evidently a
team or institutional roster entry, not a typical solo agent") but
treated it as a one-off to sanity-check and explain away, not a
structural problem needing a fix. Investigation in the sibling
`../Likelihood_to_Leave_Algorithm` project (see that project's
`modeling/HANDOFF.md`, "Team-account contamination" section, 2026-07-24)
found the same root cause applies directly here, since both projects
share the identical source columns (`volume_12m`, `units_12m`) that
`build_targets` self-joins on to construct `target_volume_next_12m` /
`target_units_next_12m`.

**The mechanism**: team members each get their own separate
`agent_profile_id` row (confirmed empirically in the Leave project — not
a merged/collapsed row), but transaction credit concentrates onto ONE
member's row (almost certainly the MLS listing-agent-of-record), leaving
real, active teammates' rows showing near-$0 production. No field in this
data currently distinguishes a team account from an individual.

**Three concrete consequences for THIS project specifically**:
1. For the credited team row, the model forecasts an entire team's future
   business using one individual's features (their own tenure,
   `career_months`) — those don't explain team-level dynamics (team
   hiring/attrition, overall team health), which is what's actually
   driving that row's real future production.
2. For the silent teammates, the model learns "this person's future
   production ≈ $0" for real, actively-working agents — a systematic,
   silent source of forecast error for exactly the population this
   contaminates, not random noise.
3. **Likely distorts the calibration/range work specifically** (rounds
   3-4, 13-14): the quantile/CQR machinery assumes quarter-to-quarter
   volatility reflects genuine personal variation. A phantom teammate
   stuck at $0 for years reads as falsely LOW volatility (not
   "absence of volatility" the way it should), which could be quietly
   skewing the tercile-based coverage checks in a way nobody has
   verified, because nobody had reason to look for a team signal here
   until the Leave project's investigation surfaced it.

**Not yet fixed here — this project has zero team-awareness in its code
today** (confirmed: no team-related logic anywhere in `data.py` or
`modeling/score_agents.py`). The fix pattern being built in the Leave
project (exclude team-labeled rows from individual scoring, add a
separate team-level model, broadcast team-context features onto real
teammates once membership linkage is known) is blocked there on an
incoming roster data file (individual name vs. "X's Team" name per
`agent_profile_id`, refreshed quarterly) — once that fix is proven out on
the Leave side, the same pattern needs to be replicated here:
`load_clean`/`build_targets` would need an equivalent team-exclusion +
team-level-forecast split, and `score_agents.py`'s CatBoost d3/log1p
pipeline would need to run twice (individual-only, team-only) the same
way the Leave model now needs its second team-churn model.
**Not started. Explicitly a known gap, not an oversight** — flagging here
so it isn't independently "rediscovered" and treated as a one-off
surprise the way the round-8 $162M account was.

**Do not start this here tomorrow, even once the roster file lands.**
The roster arrives in the Leave project first; that project's

### Three findings that change what should be reported

1. **R² must not be this project's headline.** It fails twice over. It is
   *population-sensitive*: putting the two placeholder records back moves it by
   **+0.044 (volume) / +0.055 (units)** — a swing five to ten times the whole
   seed-noise band, produced by 40 rows, with MAE, median APE, Spearman and
   coverage all staying flat. And on units the model **loses to naive
   persistence** (0.757 vs 0.791) while beating it on every other metric. R²
   rewards getting the big, obvious, persistent agents right, which is the part
   of this problem that requires no model at all.

2. **The metrics that hold up are the error and ranking ones.** Volume MAE is
   **12.2% better** than persistence, median APE 45.7% vs 57.1% (a **20%**
   relative reduction), Spearman 0.716 vs 0.611. Units: MAE 7.2% better, median
   APE 37.7% vs 42.9% (**12%** relative), Spearman 0.793 vs 0.732. These are
   population-stable — they barely moved across the exclusion arms.

3. **NEW DEFECT — the units bands over-cover above the 50% level, and this has
   never been flagged.** Volume calibration is excellent: 50.6 / 65.5 / 70.6 /
   75.5 / 80.8 / 94.8 against targets of 50 / 65 / 70 / 75 / 80 / 95 — every
   level within 0.8 points. Units is not: 51.7 / **72.5** / **77.2** / **82.2**
   / 85.4 / 96.1 — up to **7.5 points too wide** in the 65–75% band that
   `confidence_level_analysis.html` recommends for recruiting conversations.
   Round 4's numbers showed the same direction (80% band covering 85.8%) but it
   was read as coverage "holding at target" rather than as a miscalibration.
   A units range sold as 75% is really about 82%: not wrong in the dangerous
   direction, but wider than it needs to be, which is the exact complaint that
   makes ranges unusable in a pitch. **Not fixed here** — the conformal
   adjustment is doing what it is asked to; the likely cause is the integer,
   heavily-tied nature of a unit count making the empirical quantiles coarse.
   Worth a round of its own.

## File guide

- `modeling/data.py` — shared loader. `load_clean` (RIAR filter, drop
  leave-model/broken columns), `build_targets` (t+12mo self-join),
  `build_model_frame` (full pipeline + one-hot `office_brand`),
  `get_feature_columns`.
- `modeling/train_baseline.py` — the Ridge/naive-persistence/naive-mean
  gut-check documented above.
- `modeling/score_agents.py` — the production quarterly-refresh pipeline
  (CatBoost d3 log1p quantile + CQR); `modeling/hurdle_model.py` — its
  P(zero) half (XGBoost d4 + isotonic).
- `modeling/remeasure_accuracy.py` — **the accuracy backtest. Run this
  before quoting any number.** Imports the production forecast functions
  unmodified and scores them on a held-out 2-quarter window across 3 seeds,
  with naive persistence on the identical rows for comparison. Three
  population arms: default (production), `--legacy-exclusions` (puts `0014`
  back), `--no-exclusions` (puts all three placeholders back). Writes
  `remeasure_accuracy_results*.csv` (per-seed, per-target) and a readable
  log. Round 18 above is its output.
- `modeling/final_accuracy_check.log` — **SUPERSEDED, do not quote.** See
  round 18 for why (wrong population, unreproducible, beaten by the naive
  baseline on its own slice).
